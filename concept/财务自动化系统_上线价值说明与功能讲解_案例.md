# 第一部分 · 为什么上线这套系统

## 一、上线前的财务工作画像：六类重复劳动

一家办公设备与耗材经销企业的资金特征是：**收款渠道极度分散、单据量巨大、对手名不统一**。上线前，财务部每月在以下六类**低价值重复劳动**上消耗绝大部分工时：

| # | 重复劳动 | 上线前的实际形态 | 强度 |
|---|---|---|---|
| 1 | **多账户流水手工归集** | 3 家银行日记账 + 多个移动支付账户 + 4 个电商收款账户，各自导出、各自格式，逐笔抄录进一张 Excel | 极高，纯体力 |
| 2 | **逐笔判断科目** | 800 笔流水逐笔判断属于销售费用 / 管理费用 / 财务费用 / 应收应付…… 完全依赖个人经验 | 极高，强依赖人 |
| 3 | **对手名人工归并** | 同一家客户在不同渠道叫不同名字（全称、简称、昵称、括号全半角混用），必须人工识别归并 | 高，易错 |
| 4 | **应收应付逐笔核销** | 每笔收款要手工找到对应的销售单据去冲销，红冲还要单独处理，跨月核销极易错行 | 极高，最易出错 |
| 5 | **账龄计算与催收清单** | 逐笔算到期日、算逾期天数、分段汇总、再整理成催收名单 | 高，周期性重复 |
| 6 | **对账单与报表制作** | 220 份对账单逐户抄写，利润表 / 资产负债表逐月手工拼列 | 极高，机械性极强 |

**这六类劳动的共同特征**：

- **不产生增量价值** —— 不涉及判断业务实质、不涉及税务筹划、不涉及资金决策，纯粹是「数据搬运」。
- **强依赖个人记忆** —— 规则存在人脑里，人休假或离职，账就停。
- **错误难以发现** —— 手工抄录和核销的错误往往在月底或对账时才暴露，此时已难以追溯。
- **时间被锁死** —— 月初必须投入全部精力做月结，无法同时做分析和管理。

> **结论**：财务人员的时间被「搬运」占满，没有余力做「管理」。这就是上线本系统的根本动机。

## 二、系统定位与核心价值主张

### 2.1 一句话定位

> **把「散落在 8 类源文件里的资金流水」，自动变成「一本可核对的出纳账 + 一套应收应付底账 + 三张报表 + 一批可直接发出的对账单」。**

### 2.2 三条核心价值主张

| 价值主张 | 具体含义 |
|---|---|
| **把人从搬运里解放出来** | 系统承担 800 笔流水的采集、归类、归并、核销、制单；人只做**少量一次性裁决**与**复核**。 |
| **把经验变成可继承的规则** | 财务人员每一次判断（订正科目、校准对手）都被**永久记住**，下月自动生效，形成企业自己的规则资产，不再依赖某个人的记忆。 |
| **把「差不多」变成「可回溯」** | 报表每个数字都能追到源文件某一行；不一致的地方**单列成列**、不掩盖、不调平，问题可见、可收敛。 |

### 2.3 三条不可动摇的设计原则（讲解时务必强调）

1. **所有数字可回溯** —— 报表每个数字都能追到「源文件某一行」。系统保存全部中间结果，每次运行留一份完整快照。
2. **不猜、不编** —— 没有数据来源的项目，单元格写「待提供」而不是填 0；无法判断的科目导出「待填写」清单让人来决定。
3. **判断权归财务** —— 系统的自动结果只是**初稿**；财务人员的一次性裁决被永久记住，下月自动生效，不重复劳动。

## 四、效率提升测算（示例）

### 4.1 测算假设（示例值）

- 月度处理量：资金流水 **800 笔**、客户 **150 户**、供应商 **75 户**、对账单 **220 份**
- 「手工」= 熟练财务人员完全用 Excel 手工完成该环节
- 「系统」= 运行系统 + 人工复核与裁决，含处理「待填写 / 待校准」清单时间
- 1 人天按 8 小时有效工时计

### 4.2 月结工时对比（示例）

| 环节 | 手工（人天） | 系统（人天） | 降幅 |
|---|---:|---:|---:|
| 1. 多账户流水采集与录入 | 3.0 | 0.2 | ↓93% |
| 2. 逐笔定科目 | 2.0 | 0.3 | ↓85% |
| 3. 对手名归一化 | 1.5 | 0.2 | ↓87% |
| 4. 应收应付核销 | 3.0 | 0.3 | ↓90% |
| 5. 账龄归段与催收清单 | 1.5 | 0.1 | ↓93% |
| 6. 对账单制作与分发 | 4.0 | 0.3 | ↓93% |
| 7. 报表编制 | 2.0 | 0.2 | ↓90% |
| 8. 数据质量核对 | 1.0 | 0.3 | ↓70% |
| **合计** | **18.0** | **1.9** | **↓89%** |

> **测算结论（示例）**：月结从约 **18 人天 → 约 2 人天**，单月节省约 **16 人天**，折合每年释放 **约 190+ 人天**（≈ 1 名全职财务人员的月度工作量）。且这一部分是**纯搬运工时**的压缩，不牺牲任何财务判断。

### 4.3 工时之外的四项收益（更难被替代）

| 收益维度 | 上线前 | 上线后 |
|---|---|---|
| **准确性** | 抄录与核销错误在月结或对账时才暴露，追溯困难 | 全链路可回溯；余额差异、笔数不符自动告警 |
| **及时性** | 月结周期长，报表月中才能出 | 数据齐备当天出全套报表与预警（**每月 3 号出账**） |
| **风险控制** | 催收依赖人记，超期客户易漏催 | 15/20/30 天分级预警自动生成，**不漏项** |
| **可继承性** | 规则在人脑里，人员变动即断档 | 规则沉淀在配置库与规则表，**可交接、可迁移** |

## 五、为什么需要这 8 项功能：必要性与实用性逐项论证

> 每一项功能都对应一个**「不做会出事」**的具体场景，而不是「有了更好」。

| # | 功能模块 | 不做的后果（必要性） | 系统做法 | 带来的价值 |
|---|---|---|---|---|
| 1 | **多源账单解析** | 8 类源文件格式各异（含「伪装成 xls 的 XML」「表头不在首行」等陷阱），人工逐类处理极易漏读、错位 | 按账户配置关键词自动识别 10 个资金账户、自动匹配解析器 | 流水归集**零漏读、零错位**，格式变化也不影响 |
| 2 | **自动去重** | 同一文件反复放入、跨月文件重叠，人工难判断是否已入账 | 按「流水号 + 日期 + 收付金额」指纹比对 | **可重复运行、结果一致**，支持随时补数 |
| 3 | **对手名标准化** | 同一客户多渠道多名称，人工归并费时且易错；漏并会导致应收余额虚增 | 7 级优先级匹配（别名表 → 主数据全称 → 归一化 → 包含匹配） | 应收应付**按真实客户归并**，余额可信 |
| 4 | **智能科目分类** | 800 笔逐笔判科目，耗时长、标准不统一、换人即变口径 | 5 级优先级规则引擎，配合财务自维护的规则表 | 科目口径**统一、可复现、可解释**，且不需改代码即可调整 |
| 5 | **应收应付底账 + FIFO 核销** | 手工核销跨月极易错行，红冲处理易漏，余额不可信 | 自动建池、按日期先进先出核销、红冲自动冲减 | 逐户余额**准确**，是催收与报表的共同基础 |
| 6 | **账龄与预警** | 手算到期日与分段，工作量大且催收名单靠人回忆 | 按账期自动算到期日、6 段账龄、15/20/30 天分级预警 | 催收**有清单、有轻重缓急**，回款周期可控 |
| 7 | **对账单自动生成** | 220 份对账单逐户抄写，是月结最耗时的机械劳动 | 逐户自动生成，客户按业务员分文件夹 | 对账责任**落到业务员**，回款推进更顺 |
| 8 | **三大报表 + 看板** | 手工拼各月列易错、口径不一，管理层拿不到及时数据 | 按模板自动出表、每月自动加列；HTML 看板一屏概览 | 月结**当天出报表**，管理层决策有据 |

### 5.1 三个「必须有」的深层理由

**理由一：账目规模已经超过人工可靠处理的边界。**
每月 800 笔流水、150 户应收、75 户应付、220 份对账单——这个量级下，人工抄录的错误率不可能为零，而且错误具有**隐蔽性**（金额对上、但归属错户）。系统把「搬运」交给机器，是**规模倒逼的必然选择**。

**理由二：财务合规要求「可追溯、可复现」。**
审计与内控要求每一个报表数字都能说明来源、每一笔核销都能复算。手工方式下的追溯成本极高；系统保存全部中间结果与运行快照，**任何时点的数字都可复现**。

**理由三：企业资产不能锁在一个人的记忆里。**
分散的归类规则、对手别名、账期口径如果只存在于财务人员的经验中，人员一变动就会断档。系统把这些**沉淀为可交接、可迁移的规则资产**，是风险管理措施，不只是效率工具。

## 六、部门上线的意义

### 6.1 对财务部：从「记账员」到「管理者」的角色升级

- **月结周期**从「月中」提前到「每月 3 号出账」，把月初的体力高峰释放出来。
- **工作重心转移**：从「抄录与核对」转向**复核、分析、资金安排、客户信用管理**等真正需要财务判断的工作。
- **口径统一**：无论谁接手，同一套规则、同一个结果，不再因人而异。

### 6.2 对管理层：经营数据从「滞后」到「及时、可视」

- 每月 3 号即可拿到利润表、资产负债表、资金与应收应付全景。
- 一屏看板呈现：货币资金 / 应收 / 应付 / 预警 4 张核心卡片 + 各账户余额链 + 收支构成 + 应收应付 TOP + 预警 TOP。
- **决策有据**：资金紧不紧、哪几家该催、哪个账户异常，看板直接给出。

### 6.3 对业务与销售：回款责任到人

- 对账单与催收对账单**按业务员分文件夹输出**，责任清晰。
- 催收清单自带**余额、超龄明细、提醒级别、催收话术**，业务人员拿到即可执行，不必再问财务。

### 6.4 对公司治理：四项能力建设

| 能力 | 说明 |
|---|---|
| **账实相符** | 系统推算期末与源文件余额**逐户交叉核对**，差异单列不掩盖 |
| **口径统一** | 科目规则、账期规则、核销规则全部固化在配置中，可解释、可复现 |
| **可审计** | 每笔流水、每次核销、每次人工裁决都有记录，支持事后追溯 |
| **可继承、可迁移** | 整套系统全相对路径，可整体拷贝到新电脑；规则资产随系统一起交接 |

### 6.5 上线前后对照（一句话总结）

| 维度 | 上线前 | 上线后 |
|---|---|---|
| 月结投入 | 约 18 人天 | 约 2 人天 |
| 出账时点 | 月中 | 每月 3 号 |
| 催收方式 | 靠人回忆 | 分级预警清单，不漏项 |
| 报表可信度 | 依赖个人，追溯困难 | 全链路可回溯、可复现 |
| 人员变动风险 | 高（规则在人脑） | 低（规则在系统） |

## 七、里程碑与推进节奏

> 以下阶段划分描述**能力建设路径**，时间以「上线后第 N 个月」表示（示例）。

| 阶段 | 目标 | 关键交付 | 状态 |
|---|---|---|---|
| **一期 · 数据打通** | 让 8 类源文件「进得来、认得准」 | 文件自动识别与解析、账户体系建立、去重与排序规则、流水库 | ✅ 已达成 |
| **二期 · 分类与归并** | 让每一笔流水「有对手、有科目」 | 对手名标准化引擎、科目分类引擎、待填写与待校准通道、规则表接入 | ✅ 已达成 |
| **三期 · 核销与分发** | 让往来账「算得准、发得出」 | 应收应付底账、FIFO 核销、账龄分段、分级预警、对账单与催收对账单自动生成 | ✅ 已达成 |
| **四期 · 报表与闭环** | 让结果「出成表、看得见、可裁决」 | 利润表 / 资产负债表月度化、其他应收应付台账、HTML 看板、三个人工介入通道闭环、运行备份 | ✅ 已达成 |
| **五期 · 质量收敛**（推进中） | 让差异「逐项收窄」 | 期初余额补录、未分摊往来款逐户分摊、源余额差异清单收敛、报表「待提供」项由财务补列 | 🔄 持续推进 |

### 7.1 已取得的能力性里程碑（可直接对外陈述）

1. **一个入口** —— 双击一次，完成从「原始账单」到「全套报表 + 分发成果」的全部处理。
2. **一次裁决、永久生效** —— 人工判断写入规则库后，后续月份自动套用，不重复劳动。
3. **全链路可回溯** —— 报表每个数字可追到源文件；每次运行留存完整快照。
4. **不猜不编** —— 无来源项标「待提供」，无法判断项进「待填写」，绝不杜撰。
5. **可迁移可交接** —— 整套系统可整体拷贝运行，规则资产随系统移交。
6. **差异可见、可收敛** —— 一切口径差异单列成列并纳入「待收敛清单」，逐项推进而非掩盖。

# 第二部分 · 这套系统怎么工作

## 八、全流程一张图

系统只有一个入口：双击 **一键执行**。执行分 6 步：

```
┌─────────────────────────────────────────────────────────────────────┐
│  [0/6] 回读人工裁决（先做人、后自动，保证人的意志优先）              │
│        ├ 读《出纳账汇总》黄色订正列 → 科目订正 / 对手订正            │
│        ├ 读桌面《分类待填写表》      → 科目订正                      │
│        └ 读桌面《待校准对手填写表》  → 对手标准名 / 科目 / 忽略      │
├─────────────────────────────────────────────────────────────────────┤
│  [1/6] 扫描导入目录 → 按类型分派解析器 → 标准化 → 去重合并           │
│        产出：全量流水（统一字段，含日期/时间戳/源文件行序/单号）      │
├─────────────────────────────────────────────────────────────────────┤
│  [2/6] 对手名标准化 + 收支分类 + 待校准清单汇总                      │
│        产出：匹配状态（已匹配/待校准/无需校准/已归类）                │
├─────────────────────────────────────────────────────────────────────┤
│  [3/6] 应收应付底账 → FIFO 核销 → 账龄分段 → 预警清单                │
│        产出：应收/应付底账 / 账龄 / 预警清单 / 月末快照              │
├─────────────────────────────────────────────────────────────────────┤
│  [4/6] 生成 Excel 报表                                                │
│        ├ 《出纳账汇总》（4 表，含可填写订正列）                      │
│        ├ 《应收应付与账龄》（6 主表 + 隐藏钻取明细）                 │
│        ├ 《财务报表》（利润表 / 资产负债表，每月自动加列）           │
│        ├ 桌面「催收对账单」（按业务员分文件夹）                      │
│        ├ 桌面「其他应收款台账 / 其他应付款台账」                     │
│        └ 预警清单（带时间戳）                                        │
├─────────────────────────────────────────────────────────────────────┤
│  [5/6] 生成对账单（每客户 / 每供应商一份，客户按业务员分文件夹）      │
├─────────────────────────────────────────────────────────────────────┤
│  [6/6] 生成 HTML 看板 + 备份快照                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键点**：`[0/6]` 必须放在最前面 —— 因为人工裁决会改变「对手标准名」，而对手标准名决定了应收应付的核销归属。

## 十、五大核心引擎的实现逻辑

### 引擎 1：文件识别与解析

系统不是「按文件名硬编码」，而是**按账户配置匹配关键词**：

- 每个账户配置「须全部命中的关键词」与「命中即排除的关键词」，命中关键词最多的账户胜出。
- 期初类文件按**文件名精确分派**（顺序不可调整）：利润表期初 → 资产负债表期初 → 往来款/应收应付明细 → 资金账户期初。

八种解析器要点：

| 解析器 | 技术难点 | 处理方式 |
|---|---|---|
| 银行日记账 | 老版 .xls 格式 | 专用读取库；表头定位「单据编号」；「昨日余额」行自动识别为**期初余额** |
| 平台官方账单 | 表头不在第一行，前若干行是说明区 | 定位「交易时间」表头行；从说明区提取昵称与**声明笔数**用于完整性校验 |
| 平台对账文件（后缀伪装） | 名为 .xls，实为 XML | 专用 XML 解析器，正确处理稀疏单元格（跳过空列不会错位） |
| 电商账单 | 首行即表头 | 定位「入账时间」 |
| 个人卡手工账 | 记账凭证式列结构 | 借方 = 资金流入、贷方 = 资金流出（已确认口径）；流水号含行号，同日同额同对手的两笔不会被误去重 |
| 进销存单据 | 表头不固定，列名有多个历史变体 | 用「行号」定位表头；列名别名兼容（往来单位/单位名称、销售成本/成本金额…） |
| 期初表 | 「项目 + 每月一列」格式 | 按「行次+累计」「期初数+项目」定位表头，逐列取值 |

**特殊字段写入备注栏（用于逐单核对）**：电商类账户分别提取「业务基础订单号」或「订单编号」写入备注栏，可与平台后台逐单核对。

### 引擎 2：去重与排序

**去重指纹**：`摘要值(流水号 | 日期 | 收入 | 支出)`。同一文件放进去跑 100 遍，结果不变。

**排序铁律**：`日期 → 完整时间戳 → 源文件行序 → 单号`。

> 这条规则是踩过坑的：平台类账单默认「最新在上」，行序与时间序相反；而按单号字符串排序时 `xxx-10` 会排在 `xxx-9` 前面。**取「末笔余额」必须按上面的顺序**，否则会取到错误的那一行。

### 引擎 3：对手名标准化（优先级从高到低）

```
① 按流水号订正           —— 最高优先，且联动：该对手名今后同类流水自动匹配
② 对手别名表             —— 财务在《待校准对手填写表》填写后永久生效
③ 电商账户收款 → 固定映射到指定电商客户
                          （前提：方向=收 且 分类含「销售收入」）
④ 与主数据全称完全一致
⑤ 归一化后一致            （忽略括号、空格、标点差异）
⑥ 全称包含匹配            （两侧均须 ≥ 4 字，防短名误命中）
⑦ 都不中 → 标记「待校准」，进清单等人裁决
```

**为什么 ⑥ 要限长度**：曾发生真实事故 —— 把**单字对手名**映射为某客户后，系统把所有含该字的对手（含 5 家公益机构共 90 余笔）整体改了名。加长度门槛后修复。**凡是「包含/子串」匹配，无论方向都必须有最小长度门槛**，这是要写进规范的铁律。

**匹配状态四态**（出纳账里的「匹配状态」列）：

| 状态 | 含义 | 是否进待校准清单 |
|---|---|---|
| 已匹配 | 已找到标准对手名 | 否 |
| 无需校准 | 财务填「忽略」 | 否 |
| 已归类 | 已按对手指定了科目，无需再校准 | 否 |
| 待校准 | 无法识别对手 | **是** |

### 引擎 4：一级/二级科目分类（5 级优先级）

```
① 按流水号订正           —— 最高优先
② 按交易对手统一指定科目
③ 规则表一（财务自维护的关键词表）
   ├ 区块一：按「摘要」关键词匹配
   └ 区块二：按「交易对手」匹配
   （若填的是「销售费用/管理费用」这类带「/」的双选 → 不自动定级，进待填写）
④ 规则表二（其他应收应付名单）：对手命中 → 进待填写（不自动定级）
⑤ 兜底：收入 → 应收账款；支出 → 应付账款
⑥ 其余 → 进待填写清单
```

**规则表由财务人员自己维护**，可随时加行、改行，每次运行重新读取，**不需要改代码**。

**关键词匹配的防误伤规则**：
- 纯拉丁短词（少于 4 字符）必须完全相等 —— 防止短词「an」误命中长名「Anna」这类包含关系
- 中文短词（如「短信」「租金」）用包含匹配，以覆盖变体
- 长名走包含匹配，短侧须 ≥ 4 字

### 引擎 5：应收应付底账 + FIFO 核销

**建池**：

| 池 | 来源 | 条件 |
|---|---|---|
| 应收开票池 | 销售明细「单位名称」 | 按客户分组，按日期排序 |
| 应收收款池 | 出纳账流水 | 方向=收 **且** 分类=销售收入 **且** 状态=已匹配 |
| 应付单据池 | 采购明细「往来单位」 | 按供应商分组 |
| 应付付款池 | 出纳账流水 | 方向=付 **且** 分类=采购付款 **且** 状态=已匹配 |

**核销规则（先进先出）**：
- 按日期先进先出，**只核销「收款日 ≥ 开票日」的收款**（不会用上月收款去冲本月单据）
- 一笔收款可跨多张单据核销，一张单据也可由多笔收款合并核销
- **负数金额行（退货/冲销）作为贷项，冲减最早未核销单据**
- 核定后剩余未核销金额 = 该户应收/应付余额

**期初未分摊挂账**：期初往来款表只有汇总金额、无逐户明细，系统单列一行「期初余额（未分摊）」，**不参与催收预警**（因为定位不到具体客户）。

**账期与到期日**：

| 账期写法 | 到期日规则 |
|---|---|
| 空 / 无账期 | 现款 → 到期日 = 单据日 |
| 「月结」 | 次月 1 号 |
| 「N 天」 | 单据日 + N 天（按 28 天月滚动，偏保守，利于预警） |
| 「N 号对账 / N 号付款」 | 近似按月结处理 |

**账龄分段**：0-30 / 31-60 / 61-90 / 91-180 / 181-360 / >360 天（报表展示时把后两段合并为「大于 180 天」）。

**预警分级**：

| 超期天数 | 提醒级别 | 颜色 |
|---|---|---|
| 到期日当天起 | 首提（月度提醒） | — |
| ≥ 15 天 | 超期 15 天提醒 | — |
| ≥ 20 天 | 超期 20 天提醒 | 黄 |
| ≥ 30 天 | 超期 30 天提醒（**最后提醒**） | 红 |

**月末快照**：系统对每个有流水的月份，按其月末日做一次截止过滤，重算应收/应付余额，供资产负债表按月列使用。

## 十二、人工介入闭环：三个填写通道

系统**不追求 100% 自动化**，而是设计三条「一次性裁决、永久生效」的通道。**这是本系统最重要的使用概念，也是「效率」与「可控」能够兼得的原因。**

### 通道 A：出纳账订正列（最常用）

位置：《出纳账汇总》→「统一出纳账」→ 黄色区三列

| 列 | 填什么 | 效果 |
|---|---|---|
| **订正-一级分类** | 正确的一级科目 | 覆盖该笔的一级分类（同时更新核销用的收支分类） |
| **订正-二级分类** | 正确的二级科目；填 `-` 表示**清空**二级；留空 = 不改动 | 覆盖该笔的二级分类 |
| **订正-对手(标准)** | 正确的客户/供应商全称 | 覆盖该笔的标准对手，且**该对手今后的同类流水自动匹配** |

规则：
- 只填需要订正的行，其余留空
- **【流水号】列是隐藏的定位键，请勿删除该列**
- 保存并关闭 Excel 后重跑系统，自动回读并写入映射库**永久生效**
- 只填二级不填一级 → 系统会跳过并报错（防脏数据）

### 通道 B：分类待填写清单（科目未定级）

位置：桌面《分类待填写表》

- 系统把**无法自动定级**的流水导出到此表（粉色列提示）
- 在黄色【一级分类】【二级分类】填写 → 重跑 → 自动回填并永久生效，该条目从表中消失

### 通道 C：待校准对手清单（对手名无法识别）

位置：桌面《待校准对手填写表》（推荐）或《出纳账汇总》「待校准对手」表

四个填写列，四种语义：

| 填写内容 | 含义 | 效果 |
|---|---|---|
| **填写-对手标准名** = 主数据里的客户/供应商全称 | 认领为该公司 | 写入别名表，该对手今后全部流水自动匹配 |
| **填写-对手标准名** = 原对手名（同名确认） | 认可该名即为标准名 | 该对手脱离待校准表 |
| **填写-对手标准名** = `忽略` | 无需校准 | 脱离待校准表，**不影响分类** |
| **填写-一级分类 / 二级分类** | 按对手统一指定科目 | 该对手全部流水按此科目归类 |

> **🔴 必须记住的一条禁区**：**电商收款账户下的对手名，一律填「忽略」，绝不能填同名。**
> 原因：系统把电商账户的收款固定映射到指定电商客户；而对手别名表的优先级**高于**这条固定规则。一旦把电商账户的对手名写成同名，该账户的收款就会从该电商客户名下被移走，连带改动其应收余额和全部对账单。这是**效率工具首要的防错设计**——把风险点固化成一条可执行的填写规则。

### 辅助通道：规则表与手工补录

| 通道 | 位置 | 用途 |
|---|---|---|
| 规则表一 | 桌面\需手动填写的摘要/对手关键词表 | 摘要关键词 / 交易对手 → 一级二级科目规则（可多区块，财务自行加行） |
| 规则表二 | 桌面\其他应收应付名单表 | 涉及其他应收/应付的公司名单（命中后进待填写，不自动定级） |
| 手工补录 | 按既定列模板 | 补录系统未覆盖的资金流水，放入导入目录即自动读取 |

### 闭环示意

```
自动处理 ──► 剩下少量「待填写 / 待校准」 ──► 财务人员一次裁决 ──► 写入映射库
   ▲                                                                    │
   └────────────────── 下月运行自动套用，不再重复劳动 ◄──────────────────┘
```

> **这个闭环是系统价值的核心**：自动化率不是一次达到 100%，而是**每月人工干预量单调递减**——因为每一次裁决都变成了下次运行的规则。

## 十三、报表口径与勾稽关系

### 13.1 利润表（本期列）口径

| 项目 | 取数来源 |
|---|---|
| 一、商品销售收入 | 《销售明细》当期「销售收入」合计 |
| 减：商品销售成本 | 《销售明细》当期「销售成本」合计 |
| 商品销售税金及附加 | 《统一出纳账》一级分类含「税金」的支出 |
| 经营费用 | 《统一出纳账》一级分类 = 销售费用 / 经营费用 / 电商费用 |
| 管理费用 | 《统一出纳账》一级分类 = 管理费用 |
| 财务费用 | 《统一出纳账》一级分类 = 财务费用 |
| 营业外收入 / 支出 | 《统一出纳账》一级分类 = 营业外收入 / 营业外支出 |
| 三、商品销售利润 | 收入 − 成本 − 税金及附加 |
| 四、营业利润 | 销售利润 − 经营费用 − 管理费用 − 财务费用 |
| 五、利润总额 | 营业利润 + 营业外收入 − 营业外支出 |
| 六、本年净利润 | = 利润总额（**未含**所得税与税金收入） |
| 历史月列 | 直接取《利润表-期初》原值 |

> **⚠ 三处「待提供」（不填 0、不杜撰）**：返利、所得税、税金收入 —— 本示例数据包内**无来源**。因此「利润总额 / 本年净利润」是**未含上述项目**的口径，低于完整口径，需财务手工补列。

### 13.2 资产负债表（本期列）口径

| 项目 | 计算式 |
|---|---|
| 现金 | 非存款类账户（移动支付、个人卡、电商收款）期末合计 |
| 银行存款 | 3 家银行账户期末合计 |
| 应收帐款 | **月末日快照**：期初未分摊挂账 + 当期销售 − 当期收款（先进先出核销后余额） |
| 应付帐款 | 同口径 |
| 其他应收款 | 期初项目挂账 + 出纳账一级分类[其他应收*]净额 + 待计提费用表借方小计 |
| 其他应付款 | 期初项目挂账 + 出纳账一级分类[其他应付*]净额 + 待计提费用表贷方小计 |
| 存货 | 期初存货 + 当期进货 − 当期销售成本 |
| 实收资本 | 取期初资产负债表最近一个有值月份 |
| 未分配利润 | 期初未分配利润 + 当期净利润 |
| 资产合计 / 负债合计 / 所有者权益合计 | 分别加总 |
| 借货平衡 | 资产合计 − 负债合计 − 所有者权益合计 |

**示例期实际结果**：

| 项目 | 金额 | 项目 | 金额 |
|---|---:|---|---:|
| 现金 | 166,100.00 | 应付帐款 | 1,100,000.00 |
| 银行存款 | 204,000.00 | 其他应付款 | 1,470,000.00 |
| 应收帐款 | 1,150,000.00 | 负债合计 | 2,570,000.00 |
| 其他应收款 | 1,164,000.00 | 实收资本 | 440,000.00 |
| 存货 | 420,000.00 | 未分配利润 | 6,000.00 |
| **资产合计** | **3,104,100.00** | 所有者权益合计 | 446,000.00 |
| | | **借货平衡** | **+88,100.00** |

### 13.3 关于「借货平衡差异」—— 要如实讲，不要掩盖

这不是勾稽错误，是三个**已知且已确认**的口径差异累积：

1. **期初往来款整体挂账**：期初表只有汇总金额、无逐户明细，系统按「期初余额（未分摊）」单列一行，无法参与逐户核销。
2. **核销池口径**：应收余额只认「分类 = 销售收入 且 已匹配」的收款（经财务裁定维持此口径），因此**应收余额高于按一级分类可核销的金额**。
3. **移动支付账户③期初差异 250.00**：期初表登记 8,000.00，源账单余额链反推 8,250.00。按财务裁定**维持期初表数**，差额作为真实差异保留在「与源余额核对」列，不抹平。

> **讲解建议**：把这项当作「**待收敛清单**」交给财务持续跟进，**不要宣称报表已完全平衡**。每解决一项，差异就收窄一笔——这正是系统「差异可见」的价值体现。

### 13.4 三处交叉核对（系统内置的防错机制）

| 核对 | 逻辑 | 不一致时 |
|---|---|---|
| 银行日记账「昨日余额」 vs 期初模板 | 两个独立来源互相印证 | 生成「期初不一致」告警进数据质量提示 |
| 平台账单「声明笔数」 vs 实际明细行数 | 检测账单是否导出完整 | 告警并提示用完整账单重新导入 |
| 系统推算期末余额 vs 源文件余额列 | 检验流水是否漏读/多读 | 「余额差异」列单列显示，**不掩盖、不调平** |

## 十五、边界、已知限制与风险控制

### 15.1 系统不做的事（要讲清，避免期望错位）

- ❌ **不做会计分录**：系统输出「出纳账 + 应收应付 + 报表」，不生成记账凭证、不做总账/明细账。
- ❌ **不处理发票与税务**：进项税额、应交税费、发票管理为后续阶段内容，报表相应栏位已预留。
- ❌ **不判断业务实质**：一笔款是借款还是货款，系统只按规则判断；判断不准就交给财务。
- ❌ **不做强制平衡校验**：资产负债表不做强制平衡（期初权益数据到位后方可启用）。
- ❌ **不替代专业判断**：重大税务、审计、合并报表事项需持证专业人士把关。

### 15.2 已知限制

| 限制 | 说明 | 缓解方式 |
|---|---|---|
| 无余额列账户的期末是推算值 | 源文件无余额字段，期末 = 期初 + Σ收 − Σ支 | 每月与平台后台余额人工核对一次 |
| 期初未导入前数字不完整 | 期末余额缺少真实起点 | 尽快补录期初资金账户表（支持分阶段补录） |
| N 天账期按 28 天月滚动 | 与自然月有 ≤3 天误差 | 偏保守（偏严），利于预警 |
| 期初往来款无逐户明细 | 无法定位到具体客户 | 单列「期初余额（未分摊）」，不进催收预警 |
| 报表有 3 项「待提供」 | 返利、所得税、税金收入本期无来源 | 由财务手工补列 |
| 借货平衡有已知差异 | 见 13.3 | 按待收敛清单逐项推进 |

### 15.3 数据安全与可恢复性

- **每次运行自动备份**：`backup/<时间戳>/` 保存全部中间数据，本身就是完整快照。
- **主报表历史归档**：`output/历史/<时间戳>/`。
- **映射库备份**：每次重大改动前自动备份映射配置。
- **可迁移**：整套系统文件夹拷到另一台电脑，装好 Python 与两个依赖库即可继续用（全相对路径）。
- **文件被占用时**：系统不强行覆盖，另存为「*_文件被占用请关闭后重跑」并提示 —— 提醒关闭 Excel 后重跑。

## 十六、术语表

| 术语 | 含义 |
|---|---|
| **统一出纳账** | 系统把所有资金账户流水合并成的单一流水表，每笔带对手、科目、单号、源余额 |
| **对手标准名** | 把原始对手名（昵称、简称）归并到主数据里的正式客户/供应商全称 |
| **待校准 / 待填写** | 两种「系统搞不定、需要人裁决」的状态，分别指对手名和科目 |
| **订正** | 财务人员在黄色列填写正确值，系统回读后写入映射库永久生效 |
| **同名确认** | 把原对手名原样填回，表示认可该名即标准名 |
| **忽略** | 表示该对手无需校准（脱离待校准表，且不影响分类） |
| **FIFO 核销** | 先进先出：收款/付款按日期顺序逐笔冲销最早的未核销单据 |
| **红冲** | 负数金额行（退货/冲销），作为贷项冲减最早未核销单据 |
| **期初未分摊挂账** | 期初只有汇总金额、无法分到具体客户的往来余额 |
| **账龄** | 从**到期日**起算的逾期天数分段（注意：不是从单据日） |
| **月末快照** | 按月末日截止过滤后重算的应收/应付余额，供资产负债表使用 |
| **源余额** | 源文件自带的账户余额（照抄，非系统推算） |
| **余额差异** | 系统推算期末 − 源余额，用于发现漏读/多读 |

### 讲解时最容易讲错的三点（自查）

1. ❌ 说「账龄是从单据日期算的」→ ✅ **是从到期日算的**（单据日 + 账期）。
